# C++ 本地后端迁移锚点

状态：提案，作为后续设计和实现的共同基准。

分支：`cpp-migration`

## 1. 背景与目标

ReplayMod Reality 当前是 Electron + TypeScript/React 应用，并同时使用 Node worker、FFmpeg、ExifTool、Python 语音 worker 和少量平台原生模块。

本次迁移不是把 TypeScript 整体替换为 C++，也不是针对某一个函数做局部加速。目标是重整本地数据处理和任务执行边界，降低应用整体的重复解析、重复派生、跨进程复制、任务编排和状态同步成本。

目标结果：

- UI 和交互仍由 Electron/TypeScript 负责。
- 本地数据摄取、派生计算、缓存和任务执行收拢到明确的 C++ core 边界。
- renderer 不再承担大规模原始数据处理和长期计算任务。
- 同一份数据尽量只解析一次、派生一次、持久化一次。
- C++ 后端支持进度、取消、错误、版本和可诊断性。
- 迁移可以分阶段交付，每阶段都能运行现有应用和测试。

## 2. 明确不做的事情

- 不整体重写 Electron、React 或现有 UI。
- 不为了换语言而改写 MapLibre、Deck.gl、WebGL shader 或 FFmpeg。
- 不把本地计算强行改造成 HTTP 服务。
- 不在没有基准数据和验收结果的情况下声称性能提升。
- 不在第一阶段迁移本地 Qwen 推理；Python/MLX 保持现状。
- 不覆盖迁移开始前已有的未提交修改。

## 3. 为什么选 C++

本项目已经存在 C/C++/Objective-C 原生构建链路，并且未来的数据处理、媒体、平台和 GPU 边界都可能需要直接复用 C/C++ 生态。C++ 可以减少跨语言绑定层，直接接入现有 native 能力和成熟库。

选择 C++ 的核心理由是工程边界和生态复用，不是假设 C++ 在所有算法上天然比 V8 快。性能是否提升必须通过相同输入、相同输出和端到端耗时验证。

C++ 的约束：

- 禁止让 C++ 直接承担 Electron UI 状态。
- 禁止以大量 JSON 数组作为大数据接口。
- 资源、线程、子进程和取消路径必须有明确所有权。
- 对外优先使用稳定的 C ABI 或独立进程协议，避免直接绑定 Electron/V8 内部对象。
- 需要跨平台的部分必须同时验证 macOS、Windows、Linux 的构建和打包路径。

## 4. 目标架构

```text
Electron renderer
  - React/UI/交互
  - 地图和 WebGL 渲染
  - 小规模显示态计算
          │
          │ 轻量 IPC：任务 ID、查询、进度、结果句柄
          ▼
Electron main
  - 窗口、权限、生命周期
  - 任务路由和后端进程管理
  - 现有 FFmpeg/ExifTool/Python 编排
          │
          │ 稳定本地协议 + 二进制数据/文件句柄
          ▼
C++ local core
  - 原始数据摄取
  - 数据清洗和标准化
  - 派生轨迹、时间轴指标和统计
  - 派生数据缓存
  - 任务进度、取消和诊断
```

第一阶段使用独立 C++ sidecar，而不是直接编译成 Electron native addon。这样可以把 core 与 V8/Electron 解耦，先稳定数据协议和生命周期；只有在基准证明 sidecar 通信成为主要瓶颈时，才评估 C ABI/N-API 嵌入。

## 5. 首要迁移边界

### 迁移到 C++ core

- CSV/轨迹数据的读取、校验、过滤、排序和标准化。
- 统一的连续内存数据集表示。
- 轨迹派生和运动处理。
- 时间轴速度、密度及其他可缓存指标。
- 派生数据缓存的格式和版本校验。
- 可取消、可报告进度的本地任务执行。

### 暂时留在 TypeScript/Electron

- React 组件和交互状态。
- MapLibre、Deck.gl、WebGL 和 shader。
- 窗口、菜单、权限和平台 UI。
- 现有存储迁移入口和用户档案业务逻辑。
- 轻量级查询、显示格式化和小数据变换。

### 暂时留在现有外部工具

- FFmpeg 视频/音频编码和转码。
- ExifTool 元数据读取。
- Python + MLX 本地语音模型推理。
- 已有 HDR、滚轮等平台原生 helper。

## 6. 数据接口原则

逻辑接口和传输格式分离：

- 控制面使用版本化消息：任务类型、参数、任务 ID、取消、进度和错误。
- 数据面使用连续内存或版本化二进制文件，不使用大规模 JSON 数组。
- 坐标、时间戳和高程使用明确的固定宽度类型。
- 每个派生数据集带有 schema version、source fingerprint、algorithm version 和生成时间。
- 结果必须可通过旧 TypeScript 实现复核，迁移期间两套实现允许并行校验。

## 7. 关键决策门

以下问题在实现前必须有证据，不凭感觉决定：

1. 端到端耗时中，解析、派生计算、IPC、序列化、缓存读写、renderer 处理各占多少。
2. 典型数据集和压力数据集的点数、文件大小、任务时长和峰值内存。
3. sidecar 启动和协议开销是否小于获得的计算收益。
4. 哪些数据需要驻留内存，哪些数据可以通过持久化派生结果查询。
5. 任务取消、应用退出和异常恢复时，C++ 后端如何保证不遗留子进程或损坏缓存。

## 8. 完成标准

迁移不能只以“C++ 编译成功”为完成标准。必须同时满足：

- 现有功能和既有测试不回归。
- C++ 与 TypeScript 对同一输入的结果在允许误差内一致。
- 大数据任务不阻塞 renderer 交互。
- 任务可取消，应用关闭时后端可回收。
- 缓存可识别版本变化并安全失效。
- macOS、Windows、Linux 的构建/打包路径有明确结果。
- 有迁移前后的端到端基准记录，包括耗时、峰值内存、IPC 数据量和重复计算次数。
