# C++ 本地后端迁移计划

本计划依赖 [C++ 本地后端迁移锚点](./cpp-migration.md)。每一阶段都先完成可观测性和验收，再进入下一阶段。

## 阶段 0：基线和范围冻结

工作内容：

- 记录代表性小、中、大数据集。
- 记录当前启动、导入、轨迹处理、时间轴交互、缓存恢复和导出的端到端耗时。
- 记录峰值内存、renderer 卡顿、IPC 次数和传输字节数。
- 将现有处理链画成实际调用图，标出重复解析和重复派生。
- 明确本阶段不修改的功能和数据格式。

验收：能够用同一批输入复现迁移前结果，并能区分 CPU、I/O、IPC、序列化和渲染耗时。

## 阶段 1：C++ sidecar 基础设施

工作内容：

- 定义 sidecar 启动、握手、版本、请求、进度、取消、错误和关闭协议。
- 建立 C++17 构建脚本和三平台产物布局。
- 在 Electron main 中加入进程生命周期管理，但不迁移业务逻辑。
- 增加异常退出、重复启动、应用关闭和超时回收测试。
- 将 sidecar 纳入 package/make 的资源打包路径。

验收：后端可被启动、探活、取消和干净关闭；不会留下孤儿进程；现有应用功能不变。

## 阶段 2：统一数据摄取

工作内容：

- 将 CSV 读取、字段校验、精度过滤、去重、排序和边界统计迁移到 C++。
- 定义统一的连续内存数据集格式。
- 设计 source fingerprint 和 schema/algorithm version。
- 让 TypeScript 先通过兼容适配层消费 C++ 结果。
- 与现有 TypeScript parser 做双跑比对。

验收：结果与现有实现一致；大文件导入的峰值内存、临时对象数量和 IPC 数据量有明确变化；缓存命中后不重复解析。

## 阶段 3：派生数据和轨迹计算

工作内容：

- 迁移 GPS 清洗、插值、平滑和姿态约束轨迹处理。
- 保留现有 TypeScript 实现作为对照实现一段时间。
- 支持任务进度、取消和分段失败诊断。
- 统一输出轨迹、上下文点和诊断信息，避免 renderer 再组装多份数组。

验收：迁移前后轨迹在规定误差内一致；处理期间 UI 保持可交互；取消和关闭行为可靠；内存峰值和端到端耗时有基准结果。

## 阶段 4：时间轴指标和缓存

工作内容：

- 将速度、密度、平滑曲线等可缓存指标移入 C++ core。
- 以时间范围、显示分辨率和算法版本作为缓存键。
- renderer 只请求当前视窗需要的结果，不持有完整计算过程。
- 评估是否需要预聚合、多分辨率索引或按需计算。

验收：拖动和缩放时间轴不会触发全量重复计算；结果和显示行为与现有版本一致；缓存命中和失效可观测。

## 阶段 5：清理旧链路

只有阶段 0–4 的结果满足验收后才执行：

- 删除已被替代的重复 TypeScript 计算路径。
- 删除不再需要的中间数组和重复缓存。
- 统一任务错误、进度和取消模型。
- 补充文档、打包说明和故障排查说明。
- 完成三平台构建和实际打包验证。

## 风险和应对

| 风险 | 应对 |
| --- | --- |
| C++ 结果与旧实现有细小差异 | 双跑、固定测试样本、明确浮点误差范围 |
| sidecar 通信抵消计算收益 | 使用二进制数据面；必要时再评估 C ABI/N-API |
| 应用退出时后端残留 | 先实现进程树回收和超时兜底，再接入业务任务 |
| 缓存格式升级导致旧数据不可读 | schema version + 安全失效 + 保留旧读取路径 |
| 三平台编译链不一致 | 每阶段都在三平台验证，不把跨平台推迟到最后 |
| 当前未提交修改产生冲突 | 迁移分支只处理迁移文件，合并前逐项解决冲突 |

## 当前执行顺序

已接通阶段 1 的构建、打包资源配置、版本握手、探活和退出路径。Electron 主进程创建窗口后发起探活。版本 1 用标准输入和标准输出各传一行 ASCII，`hello 1` 对应 `ready 1`，`ping` 对应 `pong`，关闭标准输入触发退出。任务 ID、进度和取消将在接入首个业务任务时一并实现。

运行 `npm --prefix source run check:native-core` 可用真实 C++ 进程验证接口。开发启动和打包时由 Forge 构建本机产物，需要 C++17 编译器。macOS 和 Linux 默认使用 `c++`，Windows 默认使用 MinGW-w64 的 `g++.exe`，可用 `CXX` 指定兼容编译器。

### CSV 导入试点

设置 `REPLAYMOD_NATIVE_CSV=1` 可启用足迹 CSV 的 C++ 导入。C++ 直接读取文件、校验和排序，通过 stdout 返回版本化的定宽二进制数据。TypeScript 客户端解码为现有数据集，同一次打开中的足迹和时间轴共用坐标及时间戳数组。带照片的输入和超出原生解析范围的 CSV 会交给兼容解析器。试点使用独立快照版本。同一个快照的并发请求共用一次读缓存或导入。

在 macOS 本机预热一次后交替各运行六次，取中位数。范围从读取 CSV 到返回数据集，包含 C++ 启动、传输和解码。合成样本使用逆序时间戳和十进制坐标。

| 输入 | TypeScript | C++ 经 TypeScript 接口 |
| --- | ---: | ---: |
| 仓库样本，21,496 行输入，20,819 点通过过滤 | 54.5 ms | 12.5 ms |
| 10 万行合成足迹 | 118.0 ms | 30.9 ms |
| 50 万行合成足迹 | 594.9 ms | 139.9 ms |

Electron IPC、首帧和全进程峰值内存仍需测量。试点继续通过环境变量启用，待这些链路和跨平台产物验证后再决定默认设置。

随后用 50 万点样本补测了真实 ResourceCache 和 CPU 轨迹缓冲构建。原 TypeScript 数据集快照为 35.9 MB，原生导入生成的共享数组快照为 22.4 MB。六轮中位数下，快照读取从 109.0 ms 降到 52.5 ms。CPU 轨迹缓冲构建分别为 27.6 ms 和 34.0 ms，没有观察到加速。这里的读取结果包含文件读取和反序列化，轨迹缓冲结果不含 Electron 传输和 GPU 首帧。

兼容解析器也已复用单一来源的坐标和时间戳数组。混合足迹和照片时直接合并两个有序序列，时间戳相同仍以足迹优先。已有快照可以继续读取，新写入的单来源快照采用共享数组表示。

macOS 已通过全项目类型检查和临时配置下的 Electron 集成测试。测试启用原生导入，确认 renderer 通过真实 preload IPC 读到测试 CSV 的排序结果，并在关窗后检查 Electron 与 C++ sidecar 所在的整棵进程树退出。

### 轨迹链路基线

在 macOS 用合成 GPS 和 40 Hz 姿态样本测试当前拟合实现。预热一次后取六次中位数。拟合耗时在 worker 内计时，往返从主线程发送输入到收到结果计时。该基线覆盖输入和结果的结构化克隆，以及线程调度。

| 片段和输出采样率 | 输出点数 | worker 拟合 | 线程往返 |
| --- | ---: | ---: | ---: |
| 60 秒，2 Hz | 121 | 1.2 ms | 2.3 ms |
| 10 分钟，10 Hz | 6,001 | 13.4 ms | 23.6 ms |
| 10 分钟，60 Hz | 36,001 | 30.8 ms | 50.3 ms |
| 60 分钟，60 Hz | 216,001 | 193.6 ms | 322.7 ms |

最长样本的线程往返比拟合多约 129 ms。单独克隆该对象结果约 76 ms。实际 worker 会按视频版本缓存姿态，日常请求只发送 GPS 点，因此上述往返还包含生产路径没有的姿态输入传输。ExifTool 冷启动及真实素材提取、Electron 主进程到 renderer 的耗时继续单独测量。

已接入定宽拟合结果。每个点的时间、经度、纬度和高程以 4 个 Float64 表示，另用位图区分缺失高程和显式 NaN。输出点在前、上下文点在后，按点数分隔。worker 转移两个缓冲，主进程以此格式缓存并转发到 preload，preload 还原界面所用结果。定宽快照使用独立的版本键，读取时可回退到原对象快照。

独立测试用同一份预计算结果，从 worker 收到数据后计时，并记录恢复对象的额外耗时。以下是 macOS 本机六次中位数，范围涵盖打包和 worker 到主线程的传输。序列化体积以 V8 快照编码计。

| 输出点数 | 对象传输 | 定宽传输 | 定宽传输含恢复对象 | 对象 / 定宽快照 |
| --- | ---: | ---: | ---: | ---: |
| 6,001 | 1.48 ms | 0.13 ms | 0.33 ms | 360 KB / 193 KB |
| 36,001 | 9.00 ms | 0.18 ms | 0.58 ms | 2.19 MB / 1.16 MB |
| 216,001 | 57.78 ms | 1.10 ms | 7.03 ms | 13.17 MB / 6.94 MB |

### C++ 轨迹拟合试点

设置 `REPLAYMOD_NATIVE_TRAJECTORY=1` 可让轨迹 worker 尝试 C++ 拟合，失败时回退 TypeScript。原生试点与 TypeScript 使用独立快照版本。ExifTool 提取、基础 GPS 修复、姿态预处理和回退均由现有 TypeScript 链路处理。C++ 负责约束组装、带状求解、分窗拼接及采样。

请求经标准输入发送版本、时间、采样率、轨迹锚点、种子和相机航向。C++ 通过标准输出返回点和诊断。worker 校验头部和长度，并转成既有的定宽结果格式。真实 C++ 进程已与 TypeScript 对照通过姿态约束、长缺口、窗口重叠、跨日期变更线、缺失高程和空输入用例。真实 DJI 文件的 ExifTool 与整条 Electron 轨迹链路仍待验证。

同批合成输入取六次中位数。测量涵盖拟合及输出打包，C++ 侧另含子进程启动和输入输出传输。姿态输入已经提取，数据从 worker 内开始计时。

| 片段和输出采样率 | TypeScript | C++ 试点 |
| --- | ---: | ---: |
| 60 秒，2 Hz | 1.74 ms | 5.90 ms |
| 10 分钟，10 Hz | 12.92 ms | 19.06 ms |
| 10 分钟，60 Hz | 28.75 ms | 20.76 ms |
| 60 分钟，60 Hz | 188.30 ms | 111.50 ms |

高密度输出受益，短预览和 10 Hz 样本仍适合当前 TS 路径。试点保持显式启用，后续比较按任务选后端与复用常驻进程的收益。

补测 40 Hz 姿态的一小时片段在 10 Hz 输出下，TypeScript 约 53.73 ms，C++ 约 82.50 ms。去掉姿态时分别约 37.00 ms 和 37.46 ms。选后端时应同时考虑输入姿态规模和结果密度，单看视频长度会选错。

### 原生任务回收与打包验证

CSV 导入和轨迹拟合共用子进程执行逻辑，含输出限额、超时、退出等待和应用关闭回收。新的轨迹请求会取消上一个原生拟合；已有 ExifTool 提取可继续到完成，由后续请求复用姿态缓存。取消的结果不发布也不写快照。原生进程和队列的取消路径已通过测试。

macOS arm64 已在临时目录完成 Forge 打包。直接运行包内 `Contents/Resources/replaymod-core` 已通过版本握手和探活。Windows 与 Linux 产物需在相应平台验证。

### 时间轴指标基线

用 50 万点的 1 Hz 合成轨迹模拟换视窗，每次更换范围，预热后取六次中位数。曲线采样 3,841 个位置，直方图宽 1,920 像素。测量范围只包含指标计算。

| 指标 | 10 分钟视窗 | 24 小时视窗 |
| --- | ---: | ---: |
| 平滑速度曲线 | 10.50 ms | 35.28 ms |
| 连续密度曲线 | 0.46 ms | 1.98 ms |
| 像素密度计数 | 0.11 ms | 0.11 ms |

优先处理平滑速度。复用轨迹段速度后，10 分钟视窗在同批对照中约从 10.73 ms 降到 1.74 ms。24 小时视窗仍约 37 ms，已将平滑速度曲线移到 renderer worker。worker 一次接收轨迹的定宽数组，后续只收视窗参数和发生变化的数据，返回可转移的曲线值。拖动期间保留最新待算视窗，worker 不可用时回退到同步计算。

密度和像素直方图保留现有 renderer 路径。速度曲线使用已有的 TS 算法和缓存，避免为每个视窗将整份轨迹交给 C++ 进程。指标测试已对照 worker 输出，覆盖原始轨迹复用、派生轨迹替换、缺失覆盖和速度定义。macOS Electron 集成测试通过 Vite 加载真实 worker、返回速度结果并回收进程。
